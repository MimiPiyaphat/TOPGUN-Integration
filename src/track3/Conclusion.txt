2. ตลาดและเป้าหมายทางธุรกิจ
----------------------------------------
RFQ คือคำขอซื้อ: มีผู้ซื้อ ประเภท สเปก และปริมาณที่ต้องการ

ราคาเสนอ = TV ที่ประเมินจาก sample × markup

ตลาดตรวจคุณภาพจริง และจัดความคุ้มค่าด้วยราคา / TV จริง ไม่ใช่ราคาอย่างเดียว
ผู้ซื้อมีเพดานที่ซ่อนอยู่ เสนอเกินเพดานอาจถูกปฏิเสธแม้ยังซื้อไม่เต็ม
สินค้าคงเหลือมีมูลค่า salvage 0.80 × TV ตามกติกาที่ใช้ในการทดลองนี้

เป้าหมายจึงเป็นการเพิ่มมูลค่ารวมของการขายและสินค้าคงเหลือ ไม่ใช่ลดราคา
จนขายหมดอย่างเดียว และไม่ใช่ตั้งราคาสูงที่สุดโดยไม่สนใจโอกาสขาย
การประเมินคุณภาพและคะแนน appraisal เป็นอีกส่วนหนึ่งของผลการแข่งขัน
อันดับ PR กับอันดับคะแนนรวมอาจไม่ตรงกันเมื่อคะแนน appraisal ต่างกัน

4. หลักการของ react70
----------------------------------------
4.1 ราคาเริ่มต้น
SPECIALTY, COMMERCIAL และ INSTANT เริ่ม markup = 1.00
จำ markup แยกประเภท ไม่ได้มีราคาที่เรียนรู้เฉพาะผู้ซื้อแต่ละราย

4.2 อ่าน feedback
จับคู่ผลกับข้อเสนอที่ส่งด้วย (rfq_id, lot_id) เพื่อทราบ buyer_type และสเปก
คำนวณซ้ำจากประวัติแต่ละรอบเพียงครั้งเดียว
k = max(0.5, 1.5 - จำนวนรอบที่จบ / จำนวนรอบทั้งหมด)
ในเกมปกติ ต้นเกมก้าวใหญ่กว่า ปลายเกมก้าวเล็กลง

ต่อประเภทผู้ซื้อในแต่ละรอบ ใช้ลำดับความสำคัญดังนี้:
- ถ้ามี ABOVE_LIMIT อย่างน้อยหนึ่งข้อเสนอ: ลด 0.06 × k
- มิฉะนั้น ถ้ามี OUTBID หรือ PARTIAL: ลด 0.03 × k
  ถ้าสัดส่วนปริมาณที่แพ้การแข่งขัน >= 70% ให้คูณการลดด้วย 1.5
- มิฉะนั้น ถ้าข้อเสนอทั้งหมดของประเภทนั้น ACCEPTED: เพิ่ม 0.02 × k
- กรณีอื่นไม่เปลี่ยน
สุดท้ายจำกัด markup ให้อยู่ 0.85–1.30

สัดส่วน 70% = ปริมาณที่ไม่ได้ขายจาก OUTBID/PARTIAL
              / ปริมาณเสนอที่ไม่ใช่ SPEC_MISMATCH
ABOVE_LIMIT อยู่ในตัวหาร แต่เมื่อพบจะเข้ากฎลด 0.06 ก่อนอยู่แล้ว
react70 จึงไม่ได้หมายถึงมั่นใจ 70% หรือใช้ LLM คิด 70%

ข้อจำกัด: ข้อเสนอเล็กที่เกินเพดานเพียงรายการเดียวอาจลากราคาทั้งประเภทลง
และผู้ซื้อที่ยอมจ่ายสูงกับต่ำในประเภทเดียวกันยังใช้ราคาเรียนรู้ร่วมกัน

4.3 คัดล็อตและจำสเปก
ใช้ sample ตรวจ defect, moisture และ screen ตาม RFQ
ถ้าผลจริงแจ้ง SPEC_MISMATCH จำ (ล็อต, สเปก) และไม่ส่งซ้ำไปยังสเปกเดิม
หรือสเปกที่เข้มกว่า/เท่ากันทุกมิติในเกมนั้น
ไม่ตีความผิดสเปกว่าแพ้ราคา และไม่นับในตัวหารปริมาณแข่งขัน
การไม่ส่งล็อตจึงอาจเกิดจากไม่มี RFQ ผ่านสเปก ไม่ใช่เพราะราคาสูงเสมอ

4.4 ปริมาณและลำดับ
งบแต่ละล็อต (หน่วยกระสอบ) = min(ของเหลือ,
  ceil(ของเหลือ / รอบที่เหลือ × 2))
รอบสุดท้ายงบเท่าของที่เหลือ แต่ยังต้องผ่านข้อจำกัดอื่น
แต่ละคู่ล็อต×RFQ เสนอไม่เกิน ceil(ครึ่งหนึ่งของงบล็อต)
จึงไม่ใช่เพดาน 50% แบบทศนิยมเป๊ะเมื่อจำนวนกระสอบเป็นเลขคี่
สุ่มลำดับถ่วงด้วยขนาด RFQ แล้วเรียง TV × markup จากมากไปน้อย
react70 เริ่ม RNG สำหรับลำดับนี้ด้วย seed 11 และจำสถานะต่อระหว่างรอบ
การเรียงราคาจะทับลำดับสุ่มระหว่างคู่ที่คะแนนไม่เท่ากัน
allocator บังคับปริมาณไม่เกินงบล็อต ความต้องการ RFQ และ capacity_left_kg
ทุกข้อเสนอเป็นจำนวนเต็มกระสอบ 60 กก. และไม่ส่งคู่ซ้ำ

4.5 LLM
react70_rules ไม่เรียก LLM
react70_llm เป็นอีกโหมด: โค้ดกำหนดราคา แล้ว LLM เลือก candidate และจำนวน bags
มีการตรวจ JSON/ปริมาณ/เวลา และย้อนใช้ rule เมื่อ LLM ไม่พร้อม
ไม่ใช่ให้ LLM แก้โค้ดหรือปรับราคาได้อิสระในโหมดนี้

5. หลักการของ spread1
----------------------------------------
5.1 ส่วนที่คงไว้
สูตร TV, การตรวจ sample, blacklist สเปก, PACE=2, การแบ่งงบครึ่งล็อต
และ allocator ที่ตรวจปริมาณ ใช้กลไกเดียวกับ react70
ไม่มีการเพิ่มกฎบังคับ markup <=0.92 ในรอบสุดท้ายของ spread1 ปัจจุบัน
สูตร 6 ข้อเก่าที่มี PACE=1.15 / เร่งขึ้นราคาเมื่อผู้ซื้อซื้อไม่เต็ม
จึงไม่ใช่สูตรเดียวกับโค้ด spread1 ที่นำขึ้น sandbox

5.2 ราคาเริ่มต้น
INSTANT เริ่ม 0.97 ส่วน COMMERCIAL และ SPECIALTY เริ่ม 1.00
0.97 เป็นค่ากลยุทธ์ที่เลือกจากการทดลอง ไม่ใช่เพดานประกาศของผู้จัด

5.3 เรียนรู้สองระดับ
mt = markup รายประเภท ปรับด้วยลำดับกฎแบบ react70
mb = markup รายผู้ซื้อ ปรับด้วยปริมาณที่เสนอ/ขายได้

สำหรับผู้ซื้อรายหนึ่งในรอบนั้น ตัด SPEC_MISMATCH ออก แล้วคำนวณ:
ผลต่อข้อเสนอ ABOVE_LIMIT = -0.06 × kg ที่เสนอ
ผลต่อข้อเสนออื่น = 0.02 × kg ที่ขายได้ - 0.03 × kg ที่ขายไม่ได้
delta_buyer = ผลรวม / kg ที่เสนอทั้งหมดที่ใช้ได้ × k
mb ใหม่ = clamp(mb เดิม + delta_buyer, 0.85, 1.30)

ตัวอย่าง: ขายได้ 60 กก. และ OUTBID อีก 180 กก.
delta ก่อนคูณ k = (0.02×60 - 0.03×180)/240 = -0.0175
การถ่วงแบบนี้สะท้อนผลต่อปริมาณ แทนนับทุกซองเท่ากัน

5.4 ผสมราคาที่เรียนรู้
n = จำนวนรอบที่มี feedback ใช้ได้ของผู้ซื้อคนนั้น ไม่ใช่จำนวนซอง
w = n/(n+2)
markup ที่ใช้ = w × mb + (1-w) × mt
ถ้ายังไม่เคยมีข้อมูลรายผู้ซื้อ ใช้ mt
มีข้อมูล 1 รอบให้น้ำหนัก mb 1/3; 2 รอบ 1/2; 4 รอบ 2/3
ช่วยไม่เชื่อผลรายผู้ซื้อที่มีข้อมูลน้อยเกินไป

5.5 กระจายการจัดสรร
score = TV × markup × (1 + U[-0.01, +0.01])
เรียง score มากไปน้อยก่อนจัดสรร
การสุ่ม ±1% เปลี่ยนเฉพาะลำดับความสำคัญ ไม่ได้สุ่มราคาที่ส่ง
ราคายังคง round(TV × markup, 2)
เริ่ม RNG จาก RNG ของบอท แทนเริ่มเหมือนกันทุกทีมด้วย seed 11
เวอร์ชันใช้งานจริงเก็บทั้ง RNG จัดลำดับและ RNG jitter ลง memory
แยก namespace spread1 จาก react70 เพื่อไม่ทำลายสถานะของสูตรเดิม

ผลที่ต้องการ: เก็บล็อตให้ผู้ซื้อที่คาดว่าจะจ่ายสูง แต่ไม่รุม RFQ เดียวกัน
เมื่อหลายทางเลือกมีคะแนนใกล้กัน
ข้อจำกัด: jitter อาจพาไปทางเลือกที่แย่กว่า และการชนะไม่ได้รับประกัน
เพราะเราไม่เห็นข้อเสนอคู่แข่งก่อนปิดรอบ

----------------------------------------

7.1 สิ่งที่อิงข้อมูลจริง
- สูตร TV และ salvage 0.80 จาก rules ที่เก็บไว้
- สเปก Commercial: defect <=7%, moisture <=12.5%, ไม่จำกัด screen
- สเปก Instant: defect <=15%, moisture <=14%, ไม่จำกัด screen
- sandbox snapshot ที่ใช้เป็นฐานมี 6 รอบ และไม่มี round capacity
- ขนาด RFQ สุ่มซ้ำจาก wanted_kg ที่บันทึกใน memory ของตลาด
- ทุกทีมในเกมเดียวกันได้ล็อตและ sample เหมือนกัน ตามเงื่อนไขที่นำมาใช้

7.2 สิ่งที่ยังเป็นสมมติฐานของตัวจำลอง
- 4 ล็อตต่อทีม ล็อตละสุ่ม 3–10 กระสอบ
- คุณภาพจริง: defect สุ่มสม่ำเสมอ 0.5–16%, moisture 10.5–15%, screen 12–18
- สนามฐาน 20 ทีม 6 รอบ รอบละ 8 RFQ มีผู้ซื้อ 2 รายต่อประเภท
- เมื่อเพิ่ม Specialty มี 12 RFQ และสเปกที่สมมติคือ 3%,12%,screen>=16
- ค่าเฉลี่ยเพดาน Commercial=1.04, Instant=0.92, Specialty=1.12
- ความต่างระหว่างผู้ซื้อแจกแจงปกติ sigma=.025 และต่อ RFQ sigma=.012
- สนาม 56 ทีมปรับขนาด RFQ ตามจำนวนทีมด้วยตัวคูณ n/20
- สนามมี capacity ใช้ ceil(จำนวนกระสอบเริ่มต้น/จำนวนรอบ×1.5) ต่อรอบ
- sample noise: defect sigma=.45 หรือ .90; moisture sigma=0.4 เท่าของ defect
  sample ปัดทศนิยมและมีขอบล่างตามโค้ด; screen ไม่มี noise ในตัวจำลองนี้
- คู่แข่งเป็น proxy ที่เราเขียน ไม่ใช่สำเนาคู่แข่งทุกทีมของตลาดผู้จัด

7.3 การจับคู่และการวัด
สร้าง RFQ และเพดานล่วงหน้าจาก seed เดียวกันเพื่อเทียบสูตรอย่างจับคู่
บอทเห็นเฉพาะ sample/ข้อมูลตลาดสาธารณะ ไม่เห็น actual หรือ ceiling
ตัวตัดสินตรวจสเปกจริงและเพดาน แล้วเรียงราคา/TV จริงต่ำก่อน
กรณีเสมอสุ่มลำดับและแบ่งทีละกระสอบภายในกลุ่มที่เสมอ
รายละเอียด tie-breaking นี้เป็นการจำลอง ไม่อ้างว่าเท่ากับเซิร์ฟเวอร์ทุกจุด
PR = (รายได้ + 0.80×มูลค่าจริงของสินค้าคงเหลือ) / มูลค่าจริงสต็อกเริ่มต้น
อันดับเฉลี่ยใช้ midrank เมื่อคะแนนเสมอ
Top5 นับเข้มงวด: แม้ได้ตำแหน่งท้ายกลุ่มเสมอก็ยังต้อง <=5
อันดับที่รายงานเป็นอันดับ PR ไม่ใช่คะแนนรวม appraisal ของผู้จัด
ทุกเกมตรวจไม่เกินสต็อก/โควตา/RFQ ไม่ส่งคู่ซ้ำ และสต็อกไม่ติดลบ
หลังเกมนับ structurally_unsellable_kg จากล็อตที่ไม่มี RFQ ใดรับสเปกจริงได้
ข้อมูลนี้ใช้วิเคราะห์เท่านั้น ไม่ป้อนอนาคตหรือคุณภาพจริงให้บอท

13. ประเด็นที่ควรปรับต่อ เรียงตามสิ่งที่หลักฐานรองรับ
----------------------------------------
ก. เก็บหลักฐานให้ครบก่อนสรุปอันดับ
บันทึก state ตอนเริ่ม/ปิดเกม, stock แยกล็อต, leaderboard, standings,
appraisal และ sandbox/reveal เมื่อ endpoint อนุญาต พร้อมเวลา/รหัสเกม/สูตร
เก็บก่อน reset และไม่ใช้ leaderboard ของเกมใหม่แทนเกมเก่า

ข. ป้องกันพลาด appraisal
ปรับ polling ช่วง APPRAISAL ให้ทันเวลาตาม server และบันทึกการตอบรับ
ไม่ retry ส่งประเมินอย่างไม่ตรวจ phase จนรบกวนรอบขาย
คะแนนประเมินที่เสียไม่แก้ด้วยการตั้งราคาขายใหม่อย่างเดียว

ค. ทดลองราคาเริ่ม Instant แยกรายผู้ซื้อ
เทียบ .94/.95/.97 กับสูตรปัจจุบันบน seed เดียวกันก่อน
วัด ABOVE_LIMIT, รายได้ต่อTV, PR และอันดับ ไม่ดูเพียงจำนวนซองที่ผ่าน
การลดเริ่มต้นอาจช่วยผ่านเพดานแต่ทำให้ขายถูกเกินไปในตลาดเพดานสูง

ง. การหลบ RFQ ที่แข่งขันสูง
ทดลองใช้ประวัติ bought/wanted และจำนวนข้อเสนอช่วยจัดสรร
แยกผล jitter ออกจากผล RNG อิสระ และทดสอบคู่แข่งที่ใช้ spread1 เหมือนกัน
ซื้อไม่เต็มไม่ได้แปลว่าไม่มีคู่แข่งเสมอ อาจเกิดจากสเปกหรือเพดาน
จึงไม่เพิ่มกฎเร่งขึ้นราคาเพียงเพราะเห็น bought<wanted โดยไม่ทดสอบ

จ. ความคลาดเคลื่อนคุณภาพ
ทดสอบ noise ใกล้ขอบเกรด/สเปกและ screen เพิ่ม เพราะสนามเดิมยังไม่ครอบคลุม
การเผื่อสเปกมากไปทำให้เสียโอกาสขาย; ผ่อนมากไปเสียโควตากับ SPEC_MISMATCH
ต้องใช้ข้อมูลจริงที่เผยหลังเกมเป็นตัวตรวจ ไม่ป้อน actual ให้บอทก่อนเวลา

ฉ. เปรียบเทียบกับ react70 อย่างเป็นธรรม
ทดลองสลับสูตรเป็นเกมเต็ม เก็บเงื่อนไขและจำนวนคู่แข่ง ไม่เปลี่ยนกลางเกม
เกมตลาดจริงที่คนละล็อต/คู่แข่ง/เพดานไม่ใช่ paired test แบบในแลป
ยังอ้างไม่ได้ว่าจากยอดขาย 9 เกม spread1 ชนะ react70 อย่างมีนัยสำคัญ

รายการนี้เป็นข้อเสนอทดสอบต่อ ไม่ได้หมายความว่าแก้ลงโค้ดแล้วทั้งหมด

14.2 สิ่งที่ปรับได้เฉพาะตัวจำลองของเรา
- demand, จำนวนRFQ/ผู้ซื้อ/ทีม, การแจกล็อต, noise, hidden ceilings
- ชนิดคู่แข่ง สัดส่วนสำเนา จำนวนรอบ และ capacity ใน scenario
ต้องติดป้ายว่าเป็นสมมติฐานและเปลี่ยนเพื่อทดสอบความทนทาน

14.3 ข้อจำกัดที่บอทต้องเคารพในตลาดผู้จัด
- ปริมาณ 60 กก.ต่อกระสอบ ไม่เกินสต็อก RFQ และ capacity ที่ server ส่งมา
- เวลา phase และจำนวนรอบใช้ข้อมูล server ไม่ hardcode ตารางเวลาแลป
- สเปกผู้ซื้อ actual quality, hidden ceiling, กลไกจับคู่และคะแนนเป็นของตลาด
- สูตร TV/salvage และกติกาคะแนนยึด rules ฉบับที่ใช้แข่ง ไม่แก้สูตรคะแนนเอง
- ส่ง appraisal ในช่วงที่อนุญาต และเสนอซื้อขายผ่าน API ตามสิทธิ์ทีม
- อ่าน/เรียก API ไม่เกินอัตราที่กำหนด: คู่มือระบุ 5 ครั้ง/วินาทีต่อทีม
- README ระบุห้ามส่งคำสั่งซื้อขายด้วยมือระหว่างแข่ง ให้ agent ทำเอง
- README ระบุช่วงแข่ง2–3 หากใช้ LLM ต้องใช้ gateway ผู้จัดเท่านั้น
  ไม่ใช้ LLM cloud/Ollama ภายนอกช่วงนั้น; rule-only ที่ทดสอบนี้ไม่มีการเรียก LLM
  การบังคับใช้ LLM/ข้อยกเว้นใด ๆ ต้องตรวจประกาศช่วงนั้นเพิ่มเติม
- ส่งโค้ดและ logs ตามข้อกำหนดผู้จัดเมื่อเรียกทีม ไม่ลบหลักฐานให้ผลดูดีขึ้น
